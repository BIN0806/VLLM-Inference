# ADR 0006: Phase 3 1.5B AWQ disk exception

## Status

Accepted for the live Phase 3 1.5B AWQ gate on one already-rented Vast Ubuntu 22.04 VM.

## Decision

Keep the general rental recommendation at **≥80 GiB disk, preferably 100 GiB** (`configs/pins.yaml` `host_baseline`). Do not lower that floor.

Allow a **narrow, profile-specific exception** only for `vast-k3s-replica` serving `Qwen/Qwen2.5-1.5B-Instruct-AWQ` on a VM whose measured root filesystem is **72.5 GiB total and 55 GiB free**.

Reasons:

- Vast does not allow resizing an existing instance’s disk ([Instances FAQ](https://docs.vast.ai/guides/reference/faq/instances)).
- Vast volumes cannot be attached to VM instances ([Volumes](https://docs.vast.ai/guides/instances/storage/volumes)).
- Replacing an otherwise suitable 24 GiB RTX 3090 VM to recover 7.5 GiB of the original floor is not justified when **55 GiB is free**, which is enough for the 1.5B AWQ gate.

Hard limits for this exception:

| Gate | Requirement |
|---|---|
| Before installation | ≥40 GiB free |
| After deployment and acceptance | ≥15 GiB free |

If either free-space limit is violated: **stop and report**. Do **not** silently delete caches, images, logs, or user files to satisfy the gate.

The exception **does not apply** to `vast-k3s-replica-9b` or any 9B checkpoint. That profile remains **NO-GO** on this filesystem and must not be attempted.

k3s `local-path` PVC data still persists only across **pod restarts** on this VM. It does not survive destruction of the Vast VM and is not provider-persistent storage.

## Consequences

- Preflight keeps `min_disk_gib: 80` for every profile.
- `vast-k3s-replica` may WARN instead of FAIL when total disk matches the recorded 72.5 GiB filesystem (±2 GiB) **and** free space meets the exception floors.
- Copying the exception YAML onto another profile or model does not enable it; the implementation is closed to this profile id and the 1.5B AWQ model id.
- New rentals should still follow the 80/100 GiB recommendation.
